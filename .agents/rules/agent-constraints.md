# Agent 行为约束规范

> 版本：1.0.0  
> 更新日期：2026-05-31  
> 用途：约束 AI Agent 在本项目中的行为，防止误操作

---

## 1. 权限分级

| 权限级别 | 允许操作 | 禁止操作 | 适用场景 |
|---------|---------|---------|---------|
| **只读** | 读取文件、搜索代码 | 任何写入操作 | 初次调研、问题分析 |
| **本地开发** | 本地修改| 推送到远程 | 功能开发中 |
| **PR创建** | 本地开发 + 创建PR | 直接推送到受保护分支 | 开发完成待审查 |
| **完全权限** | 所有操作 | 无 | **仅限人工** |

## 2. 禁止操作清单

### 2.1 绝对禁止（任何权限级别）

```bash
# 禁止直接推送到受保护分支
git push origin master
git push origin main
git push origin release/*

# 禁止强制推送
git push --force
git push -f

# 禁止删除远程分支
git push --delete origin <branch>

# 禁止修改远程仓库配置
git remote add/remove/set-url

# 禁止执行危险命令
git clean -fdx  # 删除所有未追踪文件
git reset --hard origin/master  # 强制重置到远程
```

### 2.2 需要用户确认的操作

```bash
# 创建分支
git branch <name>
git checkout -b <name>

# 提交代码
git commit

# 创建Pull Request
gh pr create

# 删除本地分支
git branch -D <name>

# 合并分支
git merge <branch>
```

## 3. 工作流程约束

### 3.1 开发流程

```
1. 用户明确要求 → 执行
2. 用户未明确 → 停止并询问（特例例外：当有新文件加入时，允许且应当自动维护 Keil 虚拟工程文件、包含路径并更新 clangd 相关配置，以确保代码跳转及补全功能正常）
3. 涉及远程操作 → 必须用户确认
4. 涉及提交/推送 → 展示diff供审查
```

### 3.2 提交流程

```
1. 必须由开发者主动提出提交，严禁 Agent 自主发起
2. 精准获取开发者的原子化提交需求，按规范使用中文提交
3. 提交日志要详细，必须体现代码设计意图、底层总线/外设细节与技术栈细节
4. 展示 git diff --stat 与关键文件变更，询问用户确认后执行
5. 禁止自动执行 git push
```

### 3.3 分支操作流程

```
1. 查看当前分支状态
2. 说明将要执行的操作
3. 询问用户确认
4. 用户确认后执行
```

### 3.4 编译工作流约束

**核心原则：编译结果必须报告，禁止静默处理**

#### 编译成功时

```
必须报告：
- 编译状态（成功）
- 固件大小（Flash/RAM）
- 产物路径
- 编译耗时

示例：
✅ 编译成功
  工程: SkyStar_BSP_HAL.uvprojx → 目标: SkyStar_BSP_HAL
  芯片: STM32F407VETx | 工具链: ARMCC
  固件大小: Flash ≈ 3.2 KB  RAM ≈ 8.1 KB
  产物: SkyStar_BSP_HAL.axf (728.1 KB)
```

#### 编译失败时

```
必须报告并停止：
- 编译状态（失败）
- 错误数量和类型
- 错误位置（文件:行号）
- 错误内容摘要

禁止行为：
❌ 禁止自动修改代码尝试修复
❌ 禁止静默跳过错误
❌ 禁止假设错误原因

正确流程：
1. 报告编译错误详情
2. 分析错误原因（需用户确认）
3. 提出修复方案（需用户确认）
4. 用户确认后执行修复
5. 重新编译验证
```

#### 编译警告时

```
必须报告：
- 警告数量
- 警告类型分布
- 是否影响功能

处理方式：
- 轻警告：询问用户是否需要处理
- 重要警告：报告并询问处理方式
```

#### 禁止的编译行为

| 禁止行为 | 原因 |
|---------|------|
| 编译成功不报告 | 用户需要知道结果 |
| 编译失败自动修 | 可能修错，需用户确认 |
| 静默跳过错误 | 隐藏问题，导致后续隐患 |
| 假设错误原因 | 可能误判，需分析确认 |
| 连续多次尝试修复 | 浪费token，需用户介入 |

#### 编译工作流示例

```
正确流程：
1. 执行编译
2. 解析编译结果
3. 报告结果给用户
4. 若失败：停止并询问用户
5. 若成功：询问下一步操作

错误流程（禁止）：
1. 执行编译
2. 若失败：自动修改代码
3. 再次编译
4. 若仍失败：继续修改
5. 循环直到成功或放弃
```

## 5. 代码修改约束

### 5.1 修改前必须

```
1. 理解现有代码结构和风格
2. 检查是否有相关依赖
3. 确认修改范围和影响
4. 向用户说明修改计划
```

### 5.2 修改时必须

```
1. 遵循代码规范.md
2. 保持代码风格一致
3. 添加必要的注释
4. 不删除现有注释（除非明确要求）
```

### 5.3 修改后必须

```
1. 展示修改内容
2. 说明修改原因
3. 等待用户确认
```

### 5.4 最小修改与原子化原则

1. **原子化操作**：每次改动应聚焦于单一独立的功能模块或文件，尽量避免在一次操作中跨越多个不相关的模块进行大范围修改。
2. **最小修改原则**：只改动与当前任务直接相关的最少代码，严禁自顾自地主动优化、重构或修改未授权/未要求改动的文件，防止由于大规模蔓延改动导致系统引入未知隐患或难以恢复。
3. **撤销回滚意识**：修改前明确回滚路径。如需扩大修改范围，必须事先征得用户明确同意。

## 6. 错误处理

### 6.1 遇到错误时

```
1. 停止当前操作
2. 分析错误原因
3. 向用户说明情况
4. 提供解决方案
5. 等待用户决定
```

### 6.2 禁止的行为

```
❌ 隐瞒错误继续执行
❌ 自行猜测并尝试修复
❌ 忽略用户反馈
❌ 跳过确认流程
```

## 7. 特殊场景处理

### 7.1 远程仓库污染

```
1. 立即停止所有操作
2. 向用户说明污染情况
3. 提供恢复方案（见 Docs/Git规范.md）
4. 等待用户决策
5. 禁止自行执行恢复操作
```

### 7.2 编译错误

```
1. 分析错误原因
2. 向用户说明问题
3. 提供修复建议
4. 等待用户确认后修复
```

### 7.3 依赖冲突

```
1. 分析冲突来源
2. 向用户说明冲突情况
3. 提供解决方案
4. 等待用户选择
```

## 11. STM32 硬件驱动开发与诊断规范

为避免由于大模型上下文割裂、隐式耦合文件被遗漏或编译警告缺失（如中断服务程序 WEAK 定义隐式覆盖）导致的“硬件死锁/静默无输出”等低级错误，特制定以下开发与调试硬性约束：

### 11.1 STM32 中断与 DMA 驱动开发契约

在编写任何涉及中断（Interrupts）或直接内存访问（DMA）的 STM32 HAL 驱动（如 UART, SPI, I2C, CAN 等）时，Agent 必须强制执行以下跨文件闭环验证：

* **第一条：中断服务程序（ISR）显式绑定**
  * 在外设初始化代码之外，必须主动查找、打开并修改 **`Core/Src/stm32f4xx_it.c`** 文件。
  * 确保在外设对应的硬件中断服务函数中（例如 **`USART1_IRQHandler`** ），在对应的 **`USER CODE BEGIN`** 和 **`USER CODE END`** 标签内，显式挂载驱动层的处理入口（例如 **`port_uart_irq_handler`** ）。
  * 严禁默认“只要初始化了驱动文件就自动能收发中断”的假设。
* **第二条：DMA 中断与句柄绑定**
  * 若驱动使用了 DMA 传输，必须确保对应 DMA 数据流的中断处理函数中，已经正确绑定并调用了相应的 HAL DMA 中断处理程序（如 **`HAL_DMA_IRQHandler`** ）。
* **第三条：主动扫描编译警告**
  * 由于未重写的弱定义 ISR（**`[WEAK]`** ）在链接时不会报错，Agent 必须通过代码分析（而非仅仅依赖链接器）来主动核对中断函数的重写状态。

### 11.2 硬件端口静默（无数据输出）自底向上诊断 SOP

当烧录成功后，若串口或其它外设通信端口无任何数据输出，Agent 必须强制遵守以下 **“自底向上、信号链审计”** 排查步骤，严禁直接猜测环境或直接改动系统时钟等敏感配置：

* **第一步：主入口调用审计**
  * 检查 **`main.c`** 的主函数中，是否确实调用了初始化入口，且初始化入口是否在 **`SystemClock_Config`** 及外设硬件初始化之后被执行。
* **第二步：软件中断与数据链路审计**
  * 打开 **`Core/Src/stm32f4xx_it.c`**，用代码搜索/正则匹配方式验证：
    * 对应的中断函数是否存在且没有被注释。
    * 中断内是否确实调用了驱动层的处理程序。
    * 驱动层是否因初始化返回值异常而引发了隐式静静退出（例如 **`port_uart_init`** 失败导致 `printf` 闪退）。
* **第三步：隔离测试（纯硬件直发）**
  * 在时钟和外设初始化完毕后，插入一行最纯粹的硬件直接输出（例如不依赖中断和驱动框架的 **`HAL_UART_Transmit`** 阻塞发送）。
  * 重新编译并烧录，验证硬件和底层的时钟、引脚、波特率是否完全通路。
* **第四步：时钟与硬件物理审计**
  * 如果纯硬件直发依旧无响应，才允许向用户申请检查开发板物理跳线（RX/TX 交叉、GND 共地、调试器锁定等），并在此基础上有序进行 **`SystemClock_Config`** 的 HSI/HSE 隔离测试。
