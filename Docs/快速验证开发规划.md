## 1. 设计原则

1. **依赖底座先行**：先实现 **TF卡存储系统**，为后续的音频播放（数据源）以及 Bootloader 固件升级提供本地文件载体。
2. **工具链闭环**：保留 **Ymodem** 接收逻辑并提前至存储验证之后，打通电脑与开发板的快速文件传输通道。
3. **接口→驱动→Demo 严格分层**：遵守 **Board**、**Driver**、**Interface** 三层隔离原则，尤其是在 USB 协议栈和音频驱动中，将外部库（如 FatFS、USB Device Library）的包含限制在接口层或中间件配置中。
4. **测试验证自动化**：每个里程碑完成后必须注册对应的 Letter Shell 命令，通过命令交互或自动化测试脚本完成阶段验收。

## 阶段七：存储系统与数据传输（3 提交）

本阶段将原开发规划中阶段八的 **SDIO/FatFS** 提前，并与原阶段七的 **Ymodem** 及 **LVGL Demo** 整合，为后续音频和 USB 大容量存储打下数据地基。

**@[CubeMX配置]**

*   **SDIO 引脚分配**：
    *   **SDIO_D0** -> **PC8**
    *   **SDIO_D1** -> **PC9**
    *   **SDIO_D2** -> **PC10**
    *   **SDIO_D3** -> **PC11**
    *   **SDIO_CK** -> **PC12**
    *   **SDIO_CMD** -> **PD2**
    *   **TF_DET** (TF卡在位检测) -> **PD3**
*   **SDIO 模式与 DMA**：开启 **SDIO** 接口，模式选择 **4-bit Wide bus**。配置时钟分频器，使 SDIO 核心频率不高于 24MHz。在 **NVIC** 中开启 **SDIO global interrupt** 中断，使能 **DMA2 Stream 6 (RX)** 和 **DMA2 Stream 3 (TX)**，传输方向分别为外设到内存、内存到外设，数据位宽设置为 **Word**。
*   **GPIO 配置**：将 **TF_DET (PD3)** 配置为 **GPIO_Input** 输入模式，使能内部 **Pull-up (上拉)**，User Label 设定为 **TF_DET**。软件可依靠此引脚的低电平判断 SD 卡物理在位。
*   **FatFS**: 中间件列表中勾选 **FATFS**，选择 **SD Card** 模式。在配置中将 **MAX_SS (Maximum Sector Size)** 设定为 512。
*   **Project Manager**: **Minimum Stack Size** 维持在 **0x2000** (8KB)，**Minimum Heap Size** 保持 **0x1000** (4KB)。

### M27 — TF 卡 SDIO 接口与 FatFS 文件系统移植

```
feat(interface): port_sdio - SDIO 接口移植与 DMA 传输
feat(middleware): FatFS - SD 卡 FAT 文件系统挂载
```

*   **实现内容**：
    *   在 **port_sdio.c/h** 中封装 **HAL_SD** 的读写块接口，支持 DMA 异步读写。
    *   在 FatFS 自动生成的 **diskio.c** 适配层中，将读写接口对接至 **port_sdio**。
    *   **检测与动态选通**：读取 **TF_DET (PD3)** 引脚电平。当有 TF 卡插入时，该引脚电平为低，硬件模拟开关将自动将 **SDIO** 总线通路切换导通至板载 TF 卡座并点亮 **LED2**（排针上的对应总线连接断开）。软件初始化中需对此引脚状态进行检测。
    *   在 **bsp_board.c** 初始化中加入 **f_mount** 逻辑，默认开机挂载。
    *   注册 Shell 命令：**sd_ls**（列出文件目录）、**sd_read**（读取指定文件内容）、**sd_bench**（SD 卡连续读写速度压测）。
*   **验收条件**：插入带有 FAT32 分区的 TF 卡，开机挂载成功。运行 **sd_bench**，读写测试正常且不发生阻塞超时。

### M28 — Ymodem 协议与串口文件接收路由

```
feat(middleware): port_ymodem - Ymodem 协议解析与文件接收路由
```

*   **实现内容**：
    *   编写简易的 Ymodem 协议状态机，将其包含于 **port_ymodem.c/h**。
    *   **接收路由机制**：在串口控制台层引入重定向逻辑。当触发 Ymodem 接收时，挂起 Letter Shell 的字符流解析，将 **bsp_uart** 的接收缓冲区重定向至 Ymodem 解析引擎；文件接收结束或超时后，恢复控制台的正常 Shell 交互。
    *   接收到的数据分片写入 **FatFS** 对应文件中，用于通过串口往 TF 卡上传音乐或固件包。
    *   注册 Shell 命令：**ymodem_recv**（等待串口文件发送）。
*   **验收条件**：在终端输入 **ymodem_recv**，控制台挂起。通过超级终端（如 Xshell / SecureCRT）使用 Ymodem 发送一个 **test.wav** 音频文件。文件成功保存至 TF 卡根目录，控制台恢复 Shell 输入。

### M29 — Demo: LVGL 相册图片循环展示与编码器控制

```
feat(demo): app_lvgl_images_demo - LVGL 编码器控制相册展示
```

## 阶段八：音频子系统（3 提交）

本阶段完成 SPI2/I2S2 引脚物理复用的硬软件仲裁，并打通 TF 卡文件读取与 I2S 音频播放的完整链路。

**@[CubeMX配置]**

> [!IMPORTANT]
> **硬件复用冲突与开发策略**：
> STM32F407 的 **SPI2** 与 **I2S2** 共享同一物理外设内核。若在 CubeMX 中开启 **I2S2** 会强制关闭 **SPI2** 并擦除现有的 **hspi2** 初始化，导致依赖 SPI2 的 Flash 与 IMU 驱动出现大范围编译报错。
> **开发策略**：**CubeMX 维持原状不变（保持启用 SPI2）**。我们不修改 CubeMX 配置，不对其使能 I2S2。
> **代码实现**：在 **port_i2s.c** 中纯手写配置 **hi2s2** 句柄、引脚复用映射、音频锁相环 **PLLI2S** 时钟树以及 **DMA1 Stream 4 Channel 0** 的驱动初始化。
> **动态仲裁**：运行时由总线仲裁器（**bsp_bus**）管理物理模拟开关（PCA9555 控制），并动态改写引脚的复用状态（在 **GPIO_AF5_SPI2** 与 **GPIO_AF5_I2S2** 之间切换），以零侵入方式实现 SPI 与音频的分时复用。

*   **I2S2 物理引脚分配（运行中通过代码动态切换复用）**：
    *   **I2S2_WS** -> **PB9** (音频左右声道切换 / 帧同步，配置为 **GPIO_AF5_I2S2**)
    *   **I2S2_CK** -> **PB10** (I2S2 SCLK 位时钟，配置为 **GPIO_AF5_I2S2**)
    *   **I2S2_SD** -> **PC3** (音频发送数据线，配置为 **GPIO_AF5_I2S2**)
    *   **I2S2_ext_SD** -> **PC2** (音频接收数据线，配置为 **GPIO_AF6_I2S2ext**)
    *   **I2S2_MCK** -> **PC6** (ES8388_MCLK 主时钟，配置为 **GPIO_AF5_I2S2**)
*   **I2C1 控制引脚分配**（配置 ES8388 编解码器，器件地址 **0x10**，通过 CubeMX 默认配置）：
    *   **I2C1_SCL** -> **PB6**
    *   **I2C1_SDA** -> **PB7**
*   **I2S2 与 DMA 代码参数配置（代码中手写实现）**：
    *   **I2S2 模式**：配置为 **Half-Duplex Master**，音频协议选择 **I2S Philips**，数据格式为 **16-bit Data on 16-bit Frame**，目标采样率为 **44.1kHz**。
    *   **I2S2 DMA**：采用 **DMA1 Stream 4 Channel 0**，配置为 **Circular (循环) 模式**，方向为 **Memory to Peripheral**，数据宽度为 **HalfWord (16位)**。
    *   **PLLI2S 时钟**：在代码中手动设置 **PLLI2S** 时钟树参数（配置倍频/分频因子以保证输出精确音频时钟）。
*   **GPIO**: 无额外 GPIO 配置需求（音频功放芯片 **HT6872** 的使能端物理连接在 **SW7 Bit 1**，由 I2C 扩展芯片 **PCA9555** 的 **Port 0 Pin 0** 控制；**PA4** 引脚已分配给 **RELAY_CONTROL_PIN** 继电器控制，注意切勿冲突占用）。

### M30 — I2S 音频数据流接口与硬件总线仲裁

```
feat(interface): port_i2s - I2S2 接口与引脚复用硬件仲裁
```

*   **实现内容**：
    *   在 **port_i2s.c/h** 中封装 **HAL_I2S** 数据传输接口，支持 DMA 循环双缓冲发送。
    *   **总线资源仲裁（E4）**：由于板载的 **SPI2总线**（连接板载 W25Q128 Flash 和 ICM-42688-P IMU）与 **I2S2音频总线**（连接 ES8388）共享了 **PB10**, **PC2**, **PC3** 物理引脚。硬件上通过 **SW7 拨码开关的 BIT3** 进行物理选通切换。软件必须实现板级资源仲裁器中 **bsp_bus_acquire** 和 **bsp_bus_release** 针对 **BSP_BUS_SPI2_I2S2** 总线的物理和软件互斥逻辑。在激活 I2S2 之前，必须先释放并停用 SPI2（停止 IMU 采样，锁定 SPI2 并卸载挂载的底层驱动），再配置 **dev_pca9555** 切换模拟开关到音频侧，重新配置和初始化 I2S2 通道。
    *   注册 Shell 命令：**audio_bus_switch**（在 IMU 与 I2S 总线之间手动切换）。
*   **验收条件**：调用命令切换至音频总线后，物理示波器测量 I2S 各时钟引脚波形正常，且 IMU 的 SPI 读取逻辑进入挂起/锁定状态。

### M31 — ES8388 编解码驱动与功放使能

```
feat(driver): dev_es8388 - I2C 控制通道驱动与音量调节
feat(driver): dev_amp_ht6872 - PCA9555 控制的功放使能
```

*   **实现内容**：

    *   实现 **dev_amp_ht6872.c/h** 驱动，通过扩展芯片 **PCA9555 Port 0 Pin 0** 控制功放引脚拉高以开启音频放大电路，并提供开启/关闭的静音接口。
    *   注册 Shell 命令：**audio_init**（初始化解码芯片与使能功放）、**audio_set_vol**（音量调节 0-100）。
*   **验收条件**：初始化并使能功放后，音频编解码芯片工作电流正常，功放芯片使能端（PCA9555 对应引脚）电平正确。

## 阶段九：USB 与大容量存储（2 提交）

本阶段将验证 USB 控制器硬件，并将前述实现的存储系统通过 USB MSC 接口虚拟为 U 盘设备。

**@\[CubeMX配置]**

*   **USB_OTG_FS 引脚分配**：
    *   **USB_DM** -> **PA11** (D- 数据线)
    *   **USB_DP** -> **PA12** (D+ 数据线)
*   **USB_OTG_FS 控制器**: 开启 **USB_OTG_FS** 控制器，模式选择为 **Device_Only**，启用其内部物理层收发器（VBUS 检测按板载物理电路而定，通常选择 **Disable**）。在 **NVIC** 中开启 **OTG_FS global interrupt** 中断。
*   **USB_DEVICE**: 中间件中勾选启用 **USB_DEVICE**，选择 Device Class 为 **Mass Storage Class (MSC)**。

## 阶段十：自升级 Bootloader 系统（2 提交）

本阶段作为 BSP 功能的终极验证，将前述所有的文件系统读取能力或串口传输能力，转化为设备就地自升级的可靠安全机制。

***

### M34 — 独立 Bootloader 程序与固件擦写

```
feat(bootloader): bootloader - 独立的极简引导程序
```

*   **实现内容**：
    *   建立一个完全独立的极简裸机工程（运行于 Flash 起始地址 **0x08000000**，分配空间最大 64KB，禁止包含任何复杂的后台中间件）。
    *   实现 **flash_helper.c/h**，用于封装 STM32 内部 Flash 扇区擦除和字写入操作。
    *   在启动时检测 TF 卡根目录下是否存在特定的加密/校验后固件 **app.bin**：
        1. 若存在：读取该文件，并使用内置 Flash 接口覆盖写入 APP 分区（地址 **0x08010000**）；写入完成后将该文件在 TF 卡中改名或删除以防循环升级；
        2. 若不存在：直接检查 APP 分区的首地址是否有效。
*   **验收条件**：手动放置一个测试的 **app.bin** 到 TF 卡。复位开发板，指示灯快闪（表示正在升级），随后指示灯恢复正常状态，串口输出升级成功日志。

***

### M35 — 分区跳转逻辑与双通道升级闭环

```
feat(bootloader): jump_logic - 中断向量表重映射与程序跳转
```

*   **实现内容**：
    *   实现核心的跳转函数：关闭系统所有外设时钟和 NVIC 中断，修改中断向量表偏移寄存器 **SCB->VTOR** 指向 APP 分区首地址（**0x08010000**），读取 APP 分区首地址的数据更新堆栈指针（MSP），跳转至复位向量地址。
    *   **APP 侧配合修改**：在主工程 APP 的 Keil 配置中，修改 Flash 烧录起始地址为 **0x08010000**；在 **main.c** 初始化开头重新配置 **SCB->VTOR**。
    *   **双通道升级**：支持通过 SD 卡固件自读取升级，或在 APP 中运行 **ymodem_recv** 接收固件至 TF 卡，然后软复位（调用 **NVIC_SystemReset**）以触发 Bootloader 的自动擦写更新。
*   **验收条件**：Bootloader 运行结束后能精准跳转至 APP。在 APP 运行期间使用 Ymodem 上传新版 **app.bin**，自动重启后，系统成功跑起新版本 APP。
