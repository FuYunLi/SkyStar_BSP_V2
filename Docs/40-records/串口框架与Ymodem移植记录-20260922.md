# 串口框架 V2.1 与 Ymodem V3 移植记录（含静默数据损坏根因定案）

> 日期：2026-09-22
> 分支：`fix/ymodem-write-corruption`（基点 zcode_bsp）
> 结论：**Ymodem→SD 全链路已字节级正确**（CRC32 与 PC 一致、可正常播放）。
> 单一根因：**存储后端 DMA 的 4 字节对齐契约被违反**。移植过程中另有 3 项结论被实测推翻，一并留档。

---

## 1. 起因与两个候选串口框架的取舍

原始诉求：修复"Ymodem 传入 SD 卡的 WAV 文件头部若干字节被替换、全程无错误上报"。
外部另有两套已修复的串口框架（均在 `01待处理/串口框架/`，对外 API 与 `port_uart.h` 零差异）：

| 候选 | 规模 | 关键设计 | 判定 |
|---|---|---|---|
| `qorder/V2` | 859 行 | 分工式 IRQ（IDLE 自处理 + 委托 HAL）+ F1~F13 修复 | 落选 |
| `zcode/V2`（实为 V2.1） | 813 行 | 继承 zcode V1 + 吸收 qorder V2 分工式 IRQ 与三处加固 + ErrorCode 累积共修 | **采用** |

落选 qorder 的**实测代码依据**（不是采信文档自述）：

1. `qorder:855` `port_error_notify(ctx, huart->ErrorCode)` 传入 HAL 的**累积**错误码，且 notify 路径从不清零（只在 `get_error`/`recover` 清）。后果：一次 TX DMA 错误后若上层未读 `get_error`，`HAL_UART_ERROR_DMA` 位残留，之后任何纯 RX 错误都会命中 `(err_bits & DMA) && tx_busy` → **误杀健康发送流并 `lwrb_reset` 整个待发队列**。
2. `qorder` 的 RX 自愈在 `s_rx_start_dma` 中直接归零 `dma_write_pos` 重启，**重启前不排空已收数据** → 错误前的正常字节随基准归零丢失。
3. `zcode:295-300` 快照后**立即就地清零** `huart/hdmarx/hdmatx->ErrorCode`，并用**各 DMA 句柄自身的 ErrorCode** 分别判定 rx/tx 是否真死（单条件不误伤）；`zcode:111` 重启前先 `s_rx_drain_dma_buf()`。

## 3. 根因定案：4 字节对齐是 DMA 后端的硬契约

**机制链**（每一环都有代码或实测支撑）：

1. Ymodem 载荷指针恒为 `&ctx->frame_buf[3]`（帧头占 3 字节）。
2. FatFS 对**整扇区**写是**把用户指针直达** `disk_write`（`ff.c:3677` direct-write 路径，无中间拷贝）。
3. `sd_diskio.c` → `BSP_SD_WriteBlocks_DMA((uint32_t*)buff, ...)` → **SDIO IDMA 只能按 32 位取指，丢弃地址低 2 位** → 从对齐下界开始搬运 → 整块内容位移。
4. **静默性**：CRC16 由 SDIO 对它**实际发出的字节**生成，卡复核必然通过，因此全程无错误、无超时、`f_write` 返回 FR_OK。
5. ST 在 `sd_diskio.c:65-68` 原文警告过此事，但保护开关被注释。

**为什么偏偏现在暴露**——两版 ctx 布局让"运气"变了：

| | `frame_buf` 在 ctx 内偏移 | `&frame_buf[3]` | 症状 |
|---|---|---|---|
| V1 | **9**（`uint8_t[]` 只需 1 字节对齐，无填充） | ≡ 0 mod 4，**碰巧对齐** | 头部正常，仅个别字节异常 |
| V3 | **16**（前面是 `mode/state/ops/user_data` 四个 4 字节字段） | ≡ 3 mod 4，**必然非对齐** | 整块位移，必现 |

⇒ 教训：**"对外接口签名一致"不等于"二进制契约一致"**；结构体布局变化可以静默激活一个潜伏的硬件约束。

**修复**：在 `on_write` 落盘前判定指针对齐，非对齐则经 4 字节对齐中转缓冲（`uint32_t[]` 打底）拷贝后写。代价 1 KB RAM + 每包一次 1024 字节拷贝（相对 1024 字节的 89 ms 线路时间可忽略）。同时保留连续性守卫，使未来的协议错位当场失败而非事后靠 CRC 追查。

## 4. 被实测推翻的三个结论（含我自己的）

### 4.1 「Ymodem 协议/UART 是嫌疑人」——推翻
纯 `f_write`（不经串口、不经协议栈）即可复现，且 `mod4=3` 时 1024/1024 全坏、`mod4=0` 时干净 → 与 Ymodem 无因果，Ymodem 只是**必然产生非对齐指针**的第一个使用者。

### 4.2 「存在一个与对齐无关的 36 字节岛 + flash 读不稳定」——推翻，同源假象
移植前 align 矩阵显示"对齐轮也有 7/20 出现恒定 36 字节岛"，且 flash 双趟读有 5 块不一致。
移植后（读窗改为 `uint32_t` 打底）：**对齐轮 10/10 干净，flash read-unstable = 0**。
真因是**我的取证工具自身**用了 `static uint8_t win[64]`（仅 1 字节对齐）作 DMA 读目标 → 同一契约的另一次违反。
⇒ 教训：**测量工具必须与被测对象遵守同一契约**，否则会制造不存在的缺陷；单遍读校验也不能自证清白，必须双趟自比。

### 4.3 「打开 ST 的 ENABLE_SCRATCH_BUFFER 即可根治」——推翻，不可直接用
实测开启后 **Ymodem 传输在 packet 0 即被接收端 CAN 中止**（连文件都建不起来）。
原因在其非对齐慢路径：逐扇区 `BSP_SD_WriteBlocks_DMA` 后**只等 `WriteStatus`（DMA 完成），不等 `BSP_SD_GetCardState()`**，多扇区场景下一笔写提前发出而失败。
⇒ 已在 USER CODE 区回退该宏并写明原因。若日后要走驱动级修复，需连同该等待逻辑一起补，且该文件属 CubeMX 生成、函数体不在 USER CODE 区，重生成会丢失。

## 6. 遗留与下一步

1. ~~**flash 侧 2/43 块确定性内容损坏**~~ —— **已推翻（见第 7 节）**：那不是写坏，也不是读坏，而是早期被 CAN 中止的传输留下的**残留坏文件**（其数据块已释放并被其它文件复用）。干净重传后连读多次 CRC 全等于 PC 基准。
1b. **真待修：传输中止会留下无从发现的坏文件**。`lfs_ls` 可见该文件仍在、`size` 也正确，但数据块已被复用。需要：接收失败时删除临时文件（写临时名 + 成功后 rename），或至少在各回调失败路径上 `f_unlink/lfs_remove` 并上报。
2. **建议把"落盘/读盘缓冲 4 字节对齐"升格为全工程显式契约**：要么在 `bsp_file`/`port_sdio`/`port_spi` 增加非对齐兜底（拒绝或内部中转），要么写入规范禁止把非对齐指针交给任何 DMA 后端。当前只有 Ymodem 一处做了规避，属点状修复。
3. **CubeMX 陷阱两处**：`it.c` 的 `HAL_UART_IRQHandler(&huart1)` 会被重新生成补回；`sd_diskio.c` 宏虽在 USER CODE 区但函数体不在。建议登记为维护约定。
4. **格式统一**：移植进来的 `port_uart.c`/`ymodem.c/.h` 为 K&R 大括号且 `frame_buf` 等成员与本工程 `代码规范.md` 的 Allman/命名风格不一致，需单开 `style` 批次（不做全文件 clang-format，理由同前：本仓库非任何 clang-format 版本净态）。
5. 未提交：本轮改动全部留在工作区，提交由用户发起。

## 7. 后续：flash “读不可复现”的真相（2026-09-22 同日续）

移植后 `fatfs_test crc flash/Tour_France.wav` 连读得到 5 个不同 CRC，且在 4096 的整数倍处截断，一度怀疑 SPI 读路径/电气。逐层探针结果：

| 探针 | 结果 | 推论 |
|---|---|---|
| `flash_stable`（裸 `dev_w25q_read`，4 个地址含跨 4KB 边界，共 77 次重复读） | **0 差异** | SPI2/W25Q/电气/驱动无罪 |
| `lfs_probe` A 组（单命令内 8 逐纯重复，无注入） | 成功跳读 hash 完全一致 | 单使用者时 LittleFS 确定 |
| `lfs_probe` 逐趟状态码 | `open_fail=0`、`noise_fail=0` | **排除“堆耗尽导致 open 失败”**（堆仅 3584B 是真风险，但不是本次成因）|
| 失败形态 | `st=-1` 且 `got` 为 256 的整数倍（4096 / 7936） | 是**提前返回/短读**，不是内容被改 |
| 干净重传后：`crc` 连测 4 次（两后端） | 全部 `7A6FD6F4` = PC，`short=0` | **根因是那个残留坏文件** |

**结论**：读一个“数据块已被释放并复用给其它文件”的文件，会在同一会话内一致、跨会话随那些文件变化而变化 —— 这一个原因串通了之前全部矛盾观测（“每次不一样”、“块边界截断”、“2/43 块坏”、“同一命令内两趟却一致”）。

**本案暴露的工具自身缺陷（已修）**：`fatfs_test crc` 过去只判 `rd == 0`，把**短读当作正常推进**，于是“读失败”被误报为“内容不同”，直接把我带偏了几轮。现在单独计数并打印 `short=N` 与 `SHORT read` 告警。

**方法论教训（下次先做这三件事）**
1. 先用**最底层路径**（裸读）建立“健康基线”，再逐层往上比；不要从上层现象直接推下层病因。
2. 区分三件事：**读失败 / 短读 / 内容不同**——三者病因与修法完全不同，工具必须能分开报。
3. “同一会话内一致、跨会话变化”是**状态/别名问题**的特征，不是电气噪声的特征（电气噪声应在同一会话内也不一致）。

**仍未解（独立问题）**：`imu_read` 持续 `ret = -1`。与本次链路无关（自己的 CS 与 suspend/resume 链）。下一个零成本判据：`imu_read` → `play_wav` → `imu_read`，验证是否 `bsp_imu` 恢复链未重新初始化 ICM42688。
