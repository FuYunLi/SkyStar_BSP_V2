# Ymodem 批量文件传输稳定性优化技术报告

本报告系统梳理了在 **SkyStar BSP V2** 项目中，针对大容量二进制文件批量传输至板载 **SPI Flash** 与 **SD卡** 过程中遇到的协议级和脚本级稳定性问题，详细归纳了问题根因、优化方案及边缘场景的健壮性分析。

---

## 1. 关键问题与解决方案汇总

### 1.1 载荷数据误触发 CAN 中止信号 (CAN Abort)

#### 问题表现
在批量发送包含丰富图形与字体点阵的二进制资源文件时，传输到第八个文件 **Naraka_flower.bin** 的 **9.0%**（即发送第 **13** 个数据包）时，接收端会主动发出 **CAN**（0x18）字符中止当前会话，导致后续文件全部无法传输。

#### 根因分析
1. **协议设计缺陷**：在原始的 Ymodem 接收状态机实现中，**ymodem_receive_byte** 接口无条件对每一个收到的字节进行 **0x18**（**YMODEM_CAN**）检测。
2. **数据载荷冲突**：在二进制数据流中，**0x18** 是一个合法的正常数据字节。分析 **Naraka_flower.bin** 发现，在其偏移地址 **12524** 字节处，恰好存在连续两个 **0x18 0x18** 字节。而该位置刚好被封装在第 **13** 个数据包的载荷数据区中。
3. **状态机误触发**：当协议栈解析到该载荷数据时，错误地累加了 **cancel_count** 计数器，导致接收状态机被强制更改为 **YMODEM_STATE_OFFLINE** 离线状态。

#### 解决方案
对 **Middleware/Ymodem/ymodem.c** 的取消信号判定时机进行严格限流：
* 只有当接收端处于 **frame_index == 0U**（即等待接收新数据帧的起始控制字符 **SOH** / **STX** 状态下）时，接收到 **0x18** 字节才被视作控制信号，允许累加取消计数器。
* 在帧内数据包载荷（Payload）接收过程中，完全屏蔽对 **0x18** 的中止逻辑判定，所有接收到的字节仅作为纯数据流缓存。

### 1.2 Windows GBK 终端下的 Python 解码崩溃 (UnicodeEncodeError)

#### 问题表现
在中文 Windows 系统的命令行环境下运行 Ymodem 批量发送助手脚本时，一旦 MCU 在串口中输出包含非标准 ASCII 编码（如特殊符号或非英文字符）的 Debug 调试日志，脚本便会抛出 **UnicodeEncodeError** 崩溃并直接退出。

#### 根因分析
1. 发送助手通过串口实时抓取 MCU 端的输出日志，并将其解码为 UTF-8 字符串以实现实时展示。
2. 中文 Windows 默认的命令控制台（cmd.exe）使用 **GBK** 编码（代码页 936）。
3. 当脚本调用 **print** 在控制台输出部分在 **GBK** 字符集中无法映射的 Unicode 字符时，Python 的标准输出流保护机制被触发，导致脚本强制报错中止。

#### 解决方案
在 **Other/tools/Ymodem/ymodem_sender.py** 中实现并挂载 **safe_print_mcu_debug** 辅助函数：
* 优先尝试使用标准输出。如果捕捉到编码转换异常，自动获取当前活动控制台的代码页编码（如 **GBK**），并采用 **errors='replace'** 过滤策略，将不受支持的特殊字符转换为占位问号，保障脚本运行不受干扰。

## 2. 协议栈设计与边缘场景健壮性剖析

为了评估 Ymodem 在各种极端工业现场环境下的可靠性，现对现有状态机进行边缘场景的防错机制分析：

### 2.1 物理层干扰与帧同步恢复机制
* **场景**：若 UART 物理信号线受到强电磁干扰，导致数据帧在传输过程中丢失某些字节。
* **防护设计**：
  1. **帧大小对齐保护**：接收状态机依靠 **frame_index** 累加来识别帧尾。如果字节丢失，状态机无法按时触发 CRC 校验，将持续等待。
  2. **超时重传保护**：发送端在发送数据包后，会启动 **5.0秒** 的应答超时等待。若没有收到 **ACK**，发送端会自动发起重试并重新发送该包。
  3. **冗余恢复流程**：当发送端重新发送数据包时，接收端会因为之前处于等待态而将重新发送的帧起始字节（如 **SOH**）作为旧数据帧的普通载荷读入。在读取完毕后，CRC 校验或序列号校验（**seq + seq_inv == 0xFF**）必定宣告失败。此时接收端会主动发送 **NAK** 信号并重置 **frame_index = 0**。发送端收到 **NAK** 后，下一次重发即可完美实现帧同步对齐。

### 2.2 存储介质写入阻塞与流量控制
* **场景**：在写入板载 SPI Flash 时，可能需要执行擦除（Erase Sector）操作，这会占用 CPU 几十到几百毫秒。这是否会导致 UART 接收环形缓冲区溢出？
* **防护设计**：
  * **Ymodem 协议天然的停止-等待流控**：Ymodem 是严格的单步应答协议。接收端只有在完成 **on_data_block** 存储写入回调并确认返回成功（0）后，才会向发送端发出 **ACK** 字节。在接收端未发出 **ACK** 之前，发送端会一直处于等待状态，绝不会发送下一个数据包。因此，在存储擦写阻塞期间，物理总线上是完全没有新数据流入的，彻底杜绝了 UART 缓存溢出的物理基础。

### 2.3 异常断电与未闭合文件恢复
* **场景**：在文件传输中途，开发板突然断电。
* **防护设计**：
  * 板级虚拟文件系统（VFS）在 **ymodem_receive_byte** 接收到完整文件大小后，才在 **s_ymodem_on_transfer_end** 回调中执行 **bsp_file_close** 关闭文件。
  * 如果中途异常断电或强制复位，由于文件没有执行最终的闭合与目录项更新，系统在下次启动时能够通过文件系统底层的日志机制（如 LittleFS 的元数据双缓冲区机制）进行平滑回滚，确保不会在 Flash 中遗留损坏的空指针文件或损坏文件系统。
