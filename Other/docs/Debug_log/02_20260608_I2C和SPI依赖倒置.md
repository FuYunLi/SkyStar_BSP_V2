## 问题描述

在将开发规划中的 M10-M18（I2C/SPI）开发顺序调整为优先落地 I2C 的过程中，未同步移动原本处于“阶段三”的 SPI 依赖外设 W25Q128 与 LittleFS。

如果按照该故障规划执行：
在阶段三仅配置好 `port_i2c` 物理接口的情况下，将直接开始编写 SPI 接口的 Flash 驱动 `dev_w25q.c` 和 LittleFS。此时底层完全缺失 `port_spi` 物理接口实现，从而引发编译报错，项目无法构建。

---

## 根因分析

属于典型的**工程规划阶段的依赖倒置与设计陷阱**：

在整体交换阶段三与阶段四时，只注意到了物理抽象层接口（`port_i2c` 和 `port_spi`）的顺序调换，忽略了与其绑定的设备驱动层（`dev_w25q`）的底层通信协议依然是 SPI。由于 W25Q128 驱动和 LittleFS 强依赖于 `port_spi` 提供的 SPI 通信接口，导致在尚未实现 `port_spi` 的阶段三中，这两个设备驱动成为了“无本之木”，根本无法通过编译。

## 可选解决方案

- **方案 A（采用）：精细化重组里程碑，实现两阶段完全解耦**
  - **阶段三**调整为纯粹的 I2C 专场：物理层 (`port_i2c`) + IO扩展 (`dev_pca9555`) + EEPROM (`dev_at24c02`)。将原阶段五的 EEPROM 提前，用来做阶段三的存储读写自测，完全不依赖任何 SPI 资源。
  - **阶段四**调整为纯粹的 SPI 专场：物理层 (`port_spi`) + Flash 存储 (`dev_w25q`) + 文件系统 (`LittleFS`) + LCD 液晶屏 (`dev_st7789`)，集中解决高速并发总线调试。
  - 优点：两阶段物理总线完全隔离，无任何依赖交织，开发路径平滑，测试目标明确。
  - 缺点：无。

- **方案 B：在阶段三提前部分实现 `port_spi` 的阻塞接口**
  - 阶段三保留 W25Q128，但在 M12 前临时插入一个“阻塞版”的 `port_spi` 物理层实现。
  - 优点：不需要大幅修改外设驱动的阶段归属。
  - 缺点：会导致阶段三的工作量急剧膨胀，且同一外设（SPI）的实现被强行割裂在两个阶段，违背了“聚焦单一总线”的渐进式开发初衷。

---

## 实际修复方式

采用**方案 A**。在 `Docs/开发规划.md` 中彻底解耦 I2C 和 SPI 总线下的设备依赖，将 `dev_at24c02` (I2C) 与 `dev_w25q` / `LittleFS` (SPI) 进行了对调。

修复后的规划结构：

## 举一反三

**防坑原则**：

1. **里程碑整体对调禁忌**：当在规划中对调两个开发阶段时，必须以**“物理总线”**为边界进行细粒度梳理，切忌只对调物理接口而遗漏上层驱动，必须确保“物理层 -> 驱动层 -> 应用层”的依赖关系是单向递进的。
2. **测试设备平替思维**：当高阶段的设备被移走导致当前总线缺乏“可读写、可验证存储”的设备时，应优先从后续阶段中寻找同总线的小型简单设备（如用 I2C 的 EEPROM 替代 SPI 的 Flash）进行平替，用最小的代价实现测试闭环。
3. **编译依赖检查**：在正式开始新一阶段的编码工作前，应当首先核对当前分支下，新驱动所依赖的所有底层宏定义、头文件、接口函数是否已全部就绪。
