# BUG-01 · MultiTimer 单次触发模式下续期缺失导致状态机永久停转

| **涉及模块** | `APP/tasks/app_sys_monitor.c` · `fsm_timer_cb()`                    |
| **发现手段** | 代码审查（Claude 模型辅助分析）                                      |
| **触发条件** | 系统启动后，状态机定时器第一次触发时 `g_pending_event == SYS_EVENT_NONE`（概率极高，几乎必现） |

---

## 问题描述

系统上电后，所有按键操作均无响应。串口 Shell 的 `sys_set_state` 指令可以正常调用，WS2812B 颜色与 LED 状态却从不随按键改变。

表面现象像是按键没有被扫描到，或者事件没有被写入，实际上按键回调（`key2_short_cb` 等）已经被正确触发，`g_pending_event` 也被正确赋值，但**状态机对这些事件视而不见**。

问题在于：状态机驱动定时器 `timer_fsm` 在第一次触发后就**永久停转**了，所有后续写入 `g_pending_event` 的事件永远不会被消费。

---

## 根因分析

**MultiTimer 使用的是单次触发（One-shot）模式**：`multiTimerStart` 被调用后，定时器仅触发一次回调，随后自动进入停止状态。要实现"周期轮询"语义，**必须在每次回调的末尾无条件地再次调用 `multiTimerStart` 进行续期**。

原始代码在 `event == SYS_EVENT_NONE` 时直接 `return`，错误地将续期调用放在了 `if (event != SYS_EVENT_NONE)` 分支内部。这导致：

1. 系统启动，`timer_fsm` 首次触发，调用 `fsm_timer_cb`。
2. 此时 `g_pending_event` 大概率为 `SYS_EVENT_NONE`（系统刚启动，尚无按键操作）。
3. `if (event != SYS_EVENT_NONE)` 条件为假，代码直接 `return`，**没有执行 `multiTimerStart` 续期**。
4. `timer_fsm` 停止，状态机从此不再被驱动。
5. 无论之后按键写入多少次 `g_pending_event`，都不会被消费。

这是对 MultiTimer **调度语义的根本性误解**，将其与 RTOS 任务（`while(1)` 自驱动）的行为混淆。

**核心差异对比**：

| 模型               | "无事件跳过"是否安全 | 续期方式                |
| ------------------ | -------------------- | ----------------------- |
| **MultiTimer 回调** | ❌ 不安全，等价于注销 | 回调末尾手动 `multiTimerStart` |
| **FreeRTOS 任务**   | ✅ 安全              | `while(1)` + `vTaskDelay` 自驱动 |
| **Linux timerfd**  | ✅ 安全              | 内核自动周期触发         |

## 问题代码

```c
/* 文件：APP/tasks/app_sys_monitor.c · 函数：fsm_timer_cb() */

static void fsm_timer_cb(MultiTimer *timer, void *arg)
{
    sys_event_t event = g_pending_event;
    g_pending_event   = SYS_EVENT_NONE;

    if (event != SYS_EVENT_NONE)
    {
        /* 处理事件 ... */
        switch_state(...);

        /* ❌ 错误：续期调用被包裹在条件分支内部 */
        multiTimerStart(timer, 10, fsm_timer_cb, arg);
    }
    /* ❌ 无事件时直接 return，定时器永久停转 */
}
```

---

## 可选解决方案

- **方案 A（采用）：无条件末尾续期**
  - 将 `multiTimerStart` 移至函数末尾，在 `if/else` 分支之外无条件执行。
  - 优点：语义清晰，符合 MultiTimer 的设计约定，无额外开销。
  - 缺点：无。

- **方案 B：改用周期定时器封装**
  - 对 MultiTimer 进行一层薄封装，在底层回调内自动续期后再调用用户回调，使其对外表现为"周期定时器"。
  - 优点：上层代码不再需要关心续期逻辑。
  - 缺点：引入额外封装层，对于当前项目规模属于过度设计；且项目内其他 MultiTimer 使用处也需要同步迁移。

- **方案 C：切换至 RTOS**
  - 将状态机逻辑迁移至 FreeRTOS 任务，彻底消除此类语义混淆。
  - 优点：任务模型直观，无需手动续期。
  - 缺点：当前项目处于裸机阶段，引入 RTOS 代价过大。

---

## 实际修复方式

采用**方案 A**：将 `multiTimerStart` 移至函数末尾，在所有事件处理逻辑执行完毕后无条件续期。

```c
/* 文件：APP/tasks/app_sys_monitor.c · 函数：fsm_timer_cb() */

static void fsm_timer_cb(MultiTimer *timer, void *arg)
{
    sys_event_t event = g_pending_event;
    g_pending_event   = SYS_EVENT_NONE;

    if (event != SYS_EVENT_NONE)
    {
        if (event == SYS_EVENT_MUTE_TOGGLE)
        {
            g_is_muted = !g_is_muted;
            log_i("[FSM] Mute toggled: %s", g_is_muted ? "ON" : "OFF");
        }
        else
        {
            switch (g_current_state)
            {
            case SYS_STATE_IDLE:
                if (event == SYS_EVENT_NEXT)  switch_state(SYS_STATE_WORK);
                else if (event == SYS_EVENT_ALARM) switch_state(SYS_STATE_ALARM);
                break;
            /* ... 其余 case ... */
            default:
                break;
            }
        }
    }

    /* ✅ 修复：无论有无事件，都在函数末尾无条件续期 */
    multiTimerStart(timer, 10, fsm_timer_cb, arg);
}
```

## 举一反三

**核心认知盲区**：将"有事件才处理，无事件跳过"的 RTOS 任务思维直接套用到了单次触发的裸机调度器上。

**防坑原则**：

1. **MultiTimer 黄金法则**：每一个 MultiTimer 回调函数，必须在函数末尾无条件调用 `multiTimerStart` 续期，除非你明确想要该定时器在此次触发后停止。这应当作为代码审查的必检项。

2. **潜在隐患排查**：检查项目中所有 MultiTimer 回调（`key_timer_cb`、`heartbeat_timer_cb`、`rgb_timer_cb`、`led_timer_cb` 等），确认每一个都在末尾执行了无条件续期。

3. **移植风险警告**：未来将代码从 RTOS 移植到裸机调度器（或反向）时，需要重点审查所有定时器/任务的续期逻辑，这是两种调度模型最容易产生语义错位的环节。

4. **静默失效的危险**：此 Bug 没有任何崩溃或错误日志，系统表现仅是"功能失效"而非"异常退出"，极难通过运行时现象直接定位，是典型的**静默逻辑失效**类 Bug，需要通过代码审查而非现象观察来发现。
